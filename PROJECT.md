# Паспорт проекта

## Общие сведения

**Название команды:** M1 (одиночный проект, согласован с преподавателем)  
**Название продукта:** Support Desk, сервис обращений в техническую поддержку  
**Коды участников:** `M1`  
**Статус ранней калибровки:** `черновик`

**Документы проекта:** [требования безопасности](docs/security-requirements.md), [модель угроз](docs/threat-model.md), [проектные решения](docs/design-decisions.md), [AI_USAGE.md](AI_USAGE.md)

## 1. Назначение

Support Desk принимает обращения пользователей о технических проблемах и ведет их до решения. Пользователь описывает проблему и следит за ответами. Специалист поддержки берет обращение в работу, переписывается с пользователем, ведет внутренние заметки и закрывает обращение с решением. Собственная логика сервиса определяет, кто и в каком состоянии обращения может его читать и менять, и отделяет переписку с пользователем от внутренних заметок специалистов.

## 2. Граница продукта

**В продукт входит:**

- веб-API для работы с обращениями, сообщениями и внутренними заметками;
- вход по учебной учетной записи и определение роли;
- правила переходов состояния обращения: новое, в работе, закрыто;
- хранилище учетных записей, сессий входа, обращений, сообщений и заметок (SQLite).

**Внешнее окружение и внешние системы:**

- HTTP-клиент, через который пользователь и специалист вызывают API (curl, Postman, файл `.http`);
- учебные учетные записи, которые владелец стенда задает при развертывании;
- среда выполнения .NET и файловая система для файла базы данных.

Внешних сервисов нет.

**Команда сознательно не реализует:**

- пользовательский интерфейс;
- самостоятельную регистрацию и восстановление пароля;
- вложения файлов;
- уведомления по почте и чат в реальном времени;
- переназначение обращений, роль руководителя, отчеты и поиск.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Пользователь | Человек с технической проблемой, у которого есть учебная учетная запись | Создавать обращения; просматривать список и содержимое своих обращений; писать сообщения в своем незакрытом обращении; повторно открывать свое закрытое обращение | Видеть чужие обращения; видеть внутренние заметки; брать обращения в работу, закрывать их и менять ответственного |
| Специалист поддержки | Сотрудник службы поддержки | Просматривать все обращения; брать новое обращение в работу и становиться его ответственным; писать сообщения пользователю и внутренние заметки в назначенных ему обращениях; закрывать назначенные ему обращения с решением | Писать в обращениях и закрывать обращения, назначенные другому специалисту; создавать обращения от имени пользователя |
| Без входа | Любой, кто обращается к API | Проверить работоспособность сервиса | Любые действия с обращениями |

Отправленные сообщения и заметки не изменяются и не удаляются ни одной ролью.

## 4. Сквозные сценарии

### Сценарий 1. Создание обращения и отслеживание ответа

- **Участники:** пользователь.
- **Начальное условие:** пользователь вошел под своей учетной записью.
- **Основные действия:** пользователь создает обращение с темой и описанием проблемы, получает его номер, затем открывает список своих обращений и читает ответы специалиста.
- **Результат:** обращение зарегистрировано и ждет специалиста; пользователь видит его состояние и переписку.
- **Какие данные или состояние изменяются:** создается обращение в состоянии «новое», автором записывается вошедший пользователь.

### Сценарий 2. Обработка обращения специалистом

- **Участники:** специалист поддержки, пользователь.
- **Начальное условие:** есть обращение в состоянии «новое».
- **Основные действия:** специалист берет обращение в работу и становится ответственным; задает пользователю уточняющий вопрос; пользователь отвечает в своем обращении; специалист записывает внутреннюю заметку с результатами диагностики.
- **Результат:** переписка сохранена в обращении, заметка доступна только специалистам.
- **Какие данные или состояние изменяются:** состояние «в работе», ответственный, новые сообщения и заметка.

### Сценарий 3. Закрытие и повторное открытие

- **Участники:** специалист поддержки, пользователь.
- **Начальное условие:** обращение в состоянии «в работе», специалист назначен ответственным.
- **Основные действия:** специалист записывает решение и закрывает обращение; пользователь читает решение; если проблема осталась, пользователь повторно открывает обращение с комментарием.
- **Результат:** обращение закрыто с решением либо снова находится в работе у того же специалиста.
- **Какие данные или состояние изменяются:** состояние «закрыто» или «в работе», текст решения, сообщение пользователя с комментарием.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Обращение и переписка с пользователем | Пользователь, специалисты | Посторонний узнает подробности проблемы и сведения о пользователе | Искажается история переписки, пользователь не получает нужный ответ, возникает спор о том, что было сказано |
| Внутренние заметки специалистов | Специалисты | Пользователь видит служебную оценку и детали диагностики, не предназначенные для него | Пропадают результаты диагностики, при повторном открытии специалист работает с неверными сведениями |
| Состояние, ответственный и решение | Пользователь, специалисты | Существенных последствий нет | Обращение выглядит решенным и выпадает из очереди, закрывается без участия ответственного или не может быть открыто повторно |
| Учетные записи и роли | Все пользователи сервиса | Раскрытие данных входа позволяет войти от чужого имени | Пользователь с измененной ролью получает действия специалиста и читает заметки; при недоступности учетных записей никто не может войти |

## 6. Компоненты и внешние взаимодействия

**Компоненты:**

- **Клиент:** HTTP-клиент пользователя или специалиста (curl, Postman, файл `.http`), находится вне продукта.
- **Веб-API (ASP.NET Core):** проверяет вход, определяет пользователя и роль, применяет правила доступа и переходов состояния, отдает данные обращения с учетом роли.
- **Хранилище (файл SQLite):** учетные записи с ролями, сессии входа, обращения, сообщения и заметки. К нему обращается только веб-API.

**Взаимодействия:**

1. Клиент → веб-API: данные входа; затем запросы к обращениям с признаком выполненного входа, номерами обращений и текстами.
2. Веб-API → хранилище: чтение и запись учетных записей, сессий входа, обращений, сообщений и заметок.
3. Веб-API → клиент: данные обращения; внутренние заметки попадают в ответ только специалисту.
4. При первом запуске веб-API создает учебные учетные записи по конфигурации стенда.

Фоновых процессов и внешних систем нет.

Актуальный архитектурный вид с потоками и границами доверия: [модель угроз](docs/threat-model.md#модель-продукта).

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Запрос входа | логин и пароль | пользователь или специалист | проверяет учетную запись и определяет роль |
| Параметр пути запроса | номер обращения в `/tickets/42` | пользователь или специалист | выбирает обращение для чтения или изменения |
| Тело запроса создания обращения | тема и описание проблемы | пользователь | сохраняет как содержимое нового обращения |
| Тело запроса сообщения или заметки | текст сообщения, текст заметки | пользователь, специалист | сохраняет в переписке или в заметках |
| Тело запроса закрытия или повторного открытия | текст решения, комментарий | специалист, пользователь | сохраняет решение или комментарий и меняет состояние |
| Конфигурация стенда | логин, отображаемое имя, роль и пароль начальных учебных учетных записей | владелец стенда (M1) | создает учетные записи при первом запуске |

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- вход по учебной учетной записи с определением роли;
- создание обращения и просмотр своих обращений пользователем;
- просмотр обращений и взятие нового обращения в работу специалистом;
- сообщения пользователя и специалиста в обращении;
- внутренние заметки специалиста;
- закрытие обращения с решением.

**Функции, которые можно исключить при нехватке времени:**

- повторное открытие закрытого обращения;
- фильтрацию списка обращений по состоянию;
- отметку времени последнего ответа.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** C#, .NET 10, ASP.NET Core (минимальный веб-API), SQLite через EF Core  
**Технологии, новые для команды:** EF Core  
**Внешние сервисы, необходимые для запуска:** нет  
**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** внешние сервисы не используются; все сценарии запускаются локально, файл базы SQLite создается при первом запуске.

**Что команда реализует первым, чтобы получить запускаемую версию:** веб-API с проверкой работоспособности `GET /health`, затем модель обращения и хранилище.

## 10. Локальный запуск

**Требования к окружению:** .NET SDK 10.0; Windows или Linux; свободный порт 5080. Внешние сервисы и база данных для запуска основы не нужны.

**Команды установки и запуска:**

```text
git clone https://github.com/taisiya18/support-desk-api.git
cd support-desk-api
dotnet run --project src/SupportDesk.Api
```

После запуска в консоли появляется строка `Now listening on: http://localhost:5080`. Остановка сервера: Ctrl+C.

**Команда или запрос для проверки:** во втором терминале

```text
curl.exe http://localhost:5080/health    # Windows PowerShell
curl http://localhost:5080/health        # Linux
```

**Ожидаемый результат:** ответ `200 OK` с телом `{"status":"ok"}`.

Проверка подтверждает запуск основы и не подтверждает выполнение требований безопасности.
