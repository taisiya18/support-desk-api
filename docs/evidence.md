# Свидетельства проверок

Цепочки исправлений и подтверждений свойств по проекту. Требования описаны в [требованиях безопасности](security-requirements.md), угрозы в [модели угроз](threat-model.md), решения в [проектных решениях](design-decisions.md).

## Ответ об ошибке раскрывал внутренние сведения приложения

### Проверяемое утверждение

Ответ об ошибке не должен раскрывать клиенту внутренние сведения о приложении. Требование задано в [D-03](design-decisions.md#d-03-состав-ответа-определяется-ролью-получателя), раздел “Поведение при сбое”: необработанная ошибка возвращает клиенту общий ответ без подробностей, подробности пишутся только в журнал, а страница ошибок для разработчика на стенде отключается. В модели угроз ответ об ошибке с подробностями исключения отнесен к [T-02](threat-model.md#t-02-заметки-попадают-в-ответ-пользователю-по-его-обращению).

### Исходный сценарий и наблюдение

- Объект и исходная версия: Support Desk API, commit [af6ae0c](https://github.com/taisiya18/support-desk-api/commit/af6ae0c).
- Условия: сервис запущен локально командой `dotnet run --project src/SupportDesk.Api` на Windows с .NET SDK 10 и слушает `http://localhost:5080`; окружение `Development` задано в `launchSettings.json`. Вход не выполнялся, идентификатор сессии в запросе не передавался.
- Запрос: `POST /auth/login` с заголовком `Content-Type: application/json` и телом `{broken`, то есть некорректным JSON.
- Фактический результат до изменения: ответ `400 Bad Request` с типом `text/plain`, сохраненный вместе с заголовками занял 4269 байт. В теле вернулись тип и сообщение исключения, полная трассировка стека с именами внутренних классов и абсолютный путь к файлу исходного кода на машине разработчика вида `C:\Users\<пользователь>\source\support-desk-api\src\SupportDesk.Api\Security\SessionAuthMiddleware.cs:line 24`.

### Причина и изменение

- Причина: в `Program.cs` не было обработчика ошибок. Стенд работает в окружении `Development`, а `WebApplication` в этом окружении сам подключает `DeveloperExceptionPageMiddleware`, который отдает подробности исключения клиенту. В журнале сервера сбой записан с источником `Microsoft.AspNetCore.Diagnostics.DeveloperExceptionPageMiddleware`.
- Исправляющее изменение: в `Program.cs` первым в конвейере добавлен `UseExceptionHandler`. Он перехватывает исключение раньше страницы для разработчика и возвращает общий ответ без подробностей. Ошибка разбора запроса клиента (`BadHttpRequestException`) дает код 400, остальные случаи дают 500. Подробности остаются в журнале сервера. Изменение в commit [809df94](https://github.com/taisiya18/support-desk-api/commit/809df94).
- Проверенная исправленная версия: commit [809df94](https://github.com/taisiya18/support-desk-api/commit/809df94), рабочее дерево чистое.

### Проверки и результаты

- Негативная. Тот же запрос `POST /auth/login` с телом `{broken`. Ожидался ответ без подробностей исключения. До изменения, на `af6ae0c`, пришел ответ `400` с типом `text/plain` размером 4269 байт, в нем трассировка стека и путь к файлу исходного кода. После изменения, на `809df94`, пришел ответ `400` с типом `application/json`, телом `{"error":"bad request"}` и размером 250 байт; трассировки и пути в нем нет.
- Регрессионная, выполнена на `809df94`. `GET /health` вернул `200` и `{"status":"ok"}`. `POST /auth/login` с неверным паролем вернул `401` и `{"error":"invalid login or password"}`. `POST /auth/login` с несуществующим логином вернул `401` и то же тело. `POST /auth/login` с верными данными вернул `200` и идентификатор сессии. `GET /me` с этим идентификатором вернул `200` и `{"displayName":"Пользователь один","role":"User"}`. `GET /me` с неизвестным идентификатором вернул `401`.
- Условия выполнения: Windows, .NET SDK 10, сервис на `http://localhost:5080`, запросы отправлены `curl.exe`, тела запросов взяты из файлов. Размеры ответов измерены как длина сохраненного вывода `curl.exe -i`, то есть вместе с заголовками.

### Вывод и границы

На версии `809df94` ответ на некорректный запрос не содержит трассировки стека, имен внутренних классов и пути к файлам исходного кода. Штатные сценарии входа и проверки сессии после изменения работают так же, как до него.

Границы вывода:

- проверен один путь возникновения ошибки, некорректное тело запроса. Ветка внутреннего сбоя с кодом 500 обрабатывается тем же обработчиком, но на продукте не проверялась, потому что сценария, который ее вызывает, в текущем коде нет;
- проверка не подтверждает выполнение [SR-02](security-requirements.md#sr-02-внутренние-заметки-недоступны-пользователю) в части ответов об ошибке, так как внутренних заметок в продукте пока нет. Общий ответ об ошибке будет распространяться и на них;
- страница ошибок для разработчика по-прежнему подключается в окружении `Development`. Дефект устранен тем, что исключение до нее не доходит. Если обработчик убрать или переставить ниже по конвейеру, прежнее поведение вернется.
