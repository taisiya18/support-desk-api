# Требования безопасности

Роли, сценарии и значимые данные описаны в [PROJECT.md](../PROJECT.md). Угрозы описаны в [модели угроз](threat-model.md), решения в [проектных решениях](design-decisions.md).

## Обозначения и допущения

- «Пользователь» и «специалист» означают роли из [PROJECT.md, раздел 3](../PROJECT.md#3-пользователи-и-доступные-действия). A и B обозначают двух разных пользователей, S1 и S2 двух разных специалистов.
- «Запрос отклонен» означает ответ об отказе, после которого данные и состояние обращения не изменились. Конкретные коды ответов выбраны в D-01 и D-02.
- Номер обращения, тексты и остальные данные запроса приходят от клиента, и клиент может изменить их произвольно.
- Требования не зависят от механизма входа; выбранный механизм описан в D-01.
- Допущение: заметки передаются специалисту в составе ответа на запрос обращения. Если заметки станут отдельным ресурсом API, SR-02 и ссылка на ASVS будут уточнены.
- Переназначения обращений в продукте нет ([PROJECT.md, раздел 2](../PROJECT.md#2-граница-продукта)). Если оно появится, SR-04 пересматривается.

## Требования

### SR-01. Пользователь работает только со своими обращениями

**Требование:** пользователь может просматривать обращение, писать в него сообщения и повторно открывать его, только если он автор этого обращения. Номер чужого обращения в запросе не дает доступа к нему, а список обращений пользователя содержит только его обращения.

**Обоснование:**

- актив: обращение и переписка, в них подробности проблемы и сведения о пользователе ([PROJECT.md, раздел 5](../PROJECT.md#5-значимые-данные-и-другие-объекты));
- взаимодействие: пользователь указывает номер обращения в запросе; номер виден пользователю, поэтому подставить чужой несложно;
- недопустимое событие: пользователь B читает переписку пользователя A или пишет в нее;
- последствия: сведения одного пользователя раскрываются другому, а переписка, на которую опирается специалист, искажается.

**Критерий приёмки:**

- B запрашивает обращение A по его номеру: запрос отклонен, ответ не содержит темы, описания, переписки, решения и состояния обращения A;
- B отправляет сообщение в обращение A: запрос отклонен, переписка A не изменилась;
- B отправляет запрос на повторное открытие закрытого обращения A: запрос отклонен, обращение A остается закрытым, ответ не сообщает B, что обращение закрыто;
- B запрашивает список обращений, в том числе указав в параметрах запроса автора A: в нем только обращения B;
- A открывает свое обращение и видит тему, описание, переписку и решение; сообщение A в свое незакрытое обращение сохраняется.

**Приоритет:** высокий. Нарушение раскрывает сведения одного пользователя другому в основном сценарии, а для попытки достаточно изменить номер в запросе.

**Внешний источник:** ASVS v5.0.0-8.2.2

**Связанные T / D:** T-01; D-02

### SR-02. Внутренние заметки недоступны пользователю

**Требование:** заметки специалистов не передаются пользователю ни в одном ответе API, включая ответы по его собственным обращениям. Пользователь не получает ни текст заметок, ни сведения о них: автора, время, количество. Читать заметки могут только специалисты.

**Обоснование:**

- актив: внутренние заметки со служебной оценкой и деталями диагностики ([PROJECT.md, раздел 5](../PROJECT.md#5-значимые-данные-и-другие-объекты));
- взаимодействие: пользователь законно запрашивает свое обращение и список своих обращений;
- недопустимое событие: заметка или сведения о ней попадают в ответ пользователю;
- последствия: пользователь видит служебную оценку, не предназначенную ему. Ограничения по автору обращения (SR-01) недостаточно: автор проходит его законно, а заметки относятся к тому же обращению.

**Критерий приёмки:**

- в обращении A есть сообщения и заметка специалиста; A запрашивает это обращение: ответ содержит сообщения и не содержит ни текста заметки, ни ее автора и времени;
- A запрашивает список своих обращений: ответ не содержит сведений о заметках;
- A отправляет любой запрос на чтение заметок своего обращения: запрос отклонен, сведений о заметках в ответе нет;
- запрос A завершается ошибкой, например из-за некорректного тела: ответ об ошибке не содержит сведений о заметках;
- специалист запрашивает то же обращение и видит сообщения и заметку с автором и временем.

**Приоритет:** высокий. Заметки есть в обращениях всех пользователей, и одна ошибка в составе ответа раскрывает их каждому автору.

**Внешний источник:** ASVS v5.0.0-8.2.3

**Связанные T / D:** T-02; D-03

### SR-03. Операции специалиста недоступны пользователю

**Требование:** взять обращение в работу, добавить заметку и закрыть обращение с решением может только учетная запись с ролью специалиста. Роль определяется по учетной записи, выполнившей вход; указание роли в данных запроса полномочий не меняет.

**Обоснование:**

- актив: состояние, ответственный, заметки и решение обращения ([PROJECT.md, раздел 5](../PROJECT.md#5-значимые-данные-и-другие-объекты)), роли учетных записей;
- взаимодействие: пользователь напрямую отправляет запрос к операции специалиста, в том числе для своего обращения;
- недопустимое событие: пользователь сам закрывает обращение, становится ответственным или пишет заметку;
- последствия: обращение выглядит решенным и выпадает из очереди; среди заметок появляется текст, который специалисты примут за служебный.

**Критерий приёмки:**

- A отправляет запросы на взятие в работу, добавление заметки и закрытие своего обращения: каждый запрос отклонен; состояние, ответственный, заметки и решение не изменились;
- A повторяет те же запросы, указав роль специалиста в любом поле или параметре запроса: результат тот же;
- специалист S1 берет в работу новое обращение: состояние «в работе», ответственный S1.

**Приоритет:** высокий. Нарушение дает пользователю действия другой роли во всех обращениях.

**Внешний источник:** ASVS v5.0.0-8.2.1

**Связанные T / D:** T-03; D-01, D-02

### SR-04. Специалист изменяет только назначенные ему обращения

**Требование:** писать сообщения, добавлять заметки и закрывать обращение может только специалист, назначенный его ответственным. Взять в работу можно только обращение без ответственного; повторное взятие не заменяет назначенного ответственного.

**Обоснование:**

- актив: ответственный, переписка и решение обращения ([PROJECT.md, разделы 3 и 5](../PROJECT.md#3-пользователи-и-доступные-действия));
- взаимодействие: специалист указывает номер обращения другого специалиста; читать такое обращение ему разрешено;
- недопустимое событие: S2 пишет в обращении S1, закрывает его или становится ответственным вместо S1;
- последствия: обращение закрывается без участия ответственного, пользователь получает решение от того, кто проблему не разбирал, а S1 теряет обращение из своей работы.

**Критерий приёмки:**

- обращение назначено S1; S2 пишет в нем сообщение, добавляет заметку или закрывает его: запросы отклонены; переписка, заметки, состояние и ответственный не изменились;
- S2 отправляет запрос на взятие в работу того же обращения: запрос отклонен, ответственным остается S1;
- специалист пишет сообщение, добавляет заметку или закрывает новое обращение, не взяв его в работу: запросы отклонены;
- S1 пишет сообщение, добавляет заметку и закрывает свое обращение с решением: действия выполнены, решение сохранено.

**Приоритет:** средний. Нарушитель уже имеет роль специалиста и право читать обращение. Посторонним данные не раскрываются, страдают порядок обработки и достоверность решения.

**Связанные T / D:** T-04; D-02

### SR-05. Автор записи совпадает с учетной записью, выполнившей вход

**Требование:** обращение, сообщение, заметка и решение сохраняются с автором, равным учетной записи, выполнившей вход. Указание другой учетной записи в данных запроса не меняет автора.

**Обоснование:**

- актив: авторство обращений, сообщений, заметок и решений;
- взаимодействие: клиент передает в запросе поле автора или идентификатор другой учетной записи;
- недопустимое событие: запись сохраняется от имени другого пользователя или специалиста;
- последствия: по автору обращения определяется доступ к нему (SR-01), поэтому подмена помещает обращение в список другого пользователя. Сообщение пользователя от имени специалиста дает ложные указания от лица поддержки.

**Критерий приёмки:**

- A создает обращение, указав автором B: в списке обращений B оно не появляется; если обращение создано, его автор A;
- A отправляет сообщение в свое обращение, указав автором специалиста S1: если сообщение сохранено, его автор A, и в ответах оно показывается как сообщение пользователя;
- S1 добавляет заметку или закрывает свое обращение с решением, указав автором S2: если запись сохранена, ее автор S1.

**Приоритет:** средний. Для подмены достаточно изменить поле запроса, но нарушение затрагивает достоверность отдельных записей, а не доступ к чужим данным.

**Связанные T / D:** T-05; D-01

### SR-06. Операции с обращениями доступны только после входа

**Требование:** операции с обращениями, сообщениями и заметками выполняются только для пользователя, успешно выполнившего вход. Без входа доступны только сам вход и проверка работоспособности, и они не возвращают данных обращений. Логины других учетных записей пользователю не раскрываются: ни ответ на неуспешный вход, ни ответы с данными обращений не показывают, какие логины существуют.

**Обоснование:**

- актив: все данные продукта, учетные записи;
- взаимодействие: запрос к API без признака входа, с подделанным признаком, вход с неверным паролем или несуществующим логином;
- недопустимое событие: операция выполняется без установленной учетной записи;
- последствия: сервис не может определить автора и роль, и SR-01–SR-05 перестают действовать. Ответ, который различает неверный пароль и несуществующий логин, или подпись сообщения с логином автора позволяют узнать логины специалистов, а им доступны заметки всех обращений. Второй путь найден контрпримером при обзоре решений, см. D-03.

**Критерий приёмки:**

- запрос к любой операции с обращениями (список, просмотр, создание, сообщение, заметка, взятие в работу, закрытие, повторное открытие) без признака входа, с подделанным или измененным признаком: запрос отклонен, данные не возвращены, состояние не изменилось;
- вход с неверным паролем существующей учетной записи и вход с несуществующим логином: признак входа не выдан, ответы совпадают по коду и тексту;
- A запрашивает свое обращение с сообщением специалиста S1: ответ не содержит логина S1, автор сообщения показан отображаемым именем и ролью;
- `GET /health` без входа: ответ содержит только статус работы.

**Приоритет:** высокий. На этом свойстве держатся SR-01–SR-05.

**Связанные T / D:** T-06, T-07; D-01, D-03

### SR-07. Пароли не хранятся и не выводятся в открытом виде

**Требование:** пароль учетной записи сохраняется только в виде, из которого его нельзя восстановить обратным преобразованием, и не попадает в ответы API, журнал сервера и файлы репозитория.

**Обоснование:**

- актив: данные входа учетных записей, в том числе специалистов;
- взаимодействие: копирование файла базы данных или журнала со стенда, просмотр публичного репозитория;
- недопустимое событие: пароль читается или восстанавливается без подбора;
- последствия: вход от чужого имени, в том числе как специалист, и чтение чужих обращений и заметок (SR-01, SR-02).

**Критерий приёмки:**

- после создания учебных учетных записей поиск их паролей в файле базы данных не находит совпадений, а сохраненное значение нельзя преобразовать обратно в пароль, зная код сервиса;
- после успешного и неуспешного входа пароль не встречается в ответах API и в журнале сервера;
- поиск паролей учебных учетных записей в файлах репозитория и в его истории не находит совпадений.

**Приоритет:** средний. Для нарушения нужен доступ к диску стенда или ошибка при публикации, но последствия высокие: вход с ролью специалиста.

**Связанные T / D:** T-08; D-04
