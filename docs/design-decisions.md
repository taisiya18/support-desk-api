# Проектные решения безопасности

Решения покрывают приоритетный набор угроз T-01, T-02, T-03, T-06 из [модели угроз](threat-model.md). Требования и критерии приёмки описаны в [требованиях безопасности](security-requirements.md), точки входа, границы доверия TB-1–TB-3 и допущения А1–А6 в модели угроз.

**Статус реализации:** решения относятся к планируемым частям продукта. В коде пока есть только `GET /health`. Будущие проверки описывают план и не выполнялись.

| Угроза | Требование | Решение | В приоритетном наборе |
| --- | --- | --- | --- |
| T-01 | SR-01 | D-02 | да |
| T-02 | SR-02 | D-03 | да |
| T-03 | SR-03 | D-01, D-02 | да |
| T-06 | SR-06 | D-01 | да |
| T-04 | SR-04 | D-02 | нет |
| T-05 | SR-05 | D-01 | нет |
| T-08 | SR-07 | D-04 | нет |

T-07, T-09 и T-10 имеют низкий приоритет, отдельных решений для них нет. T-07 указана в ограничениях D-01 и D-04, T-10 в ограничениях D-01, условие пересмотра T-09 записано в модели угроз.

Решения опираются друг на друга: D-02 и D-03 используют субъекта и роль, которые определяет D-01, а D-01 проверяет пароль по правилам D-04.

### D-01. Сервер определяет учетную запись и роль по серверной сессии

**Контекст:** все данные запроса приходят из-за границы TB-1, клиент может подменить в них номер, автора и роль (T-03, T-05) или отправить запрос без входа (T-06). Правила доступа D-02 и D-03 работают, только если сервер сам надежно знает, кто отправил запрос. Без решения любой клиент, отправивший запрос к API, читает и меняет обращения.

**Место в архитектуре:** процесс «Вход» и общая проверка на входе веб-API перед процессом «Операции с обращениями»; граница TB-1.

**Решение:**

- `POST /auth/login` сверяет логин и пароль с хранилищем учетных записей по правилам D-04. При успехе сервер создает сессию: случайный идентификатор длиной 128 бит из криптографически стойкого генератора и запись в хранилище с учетной записью и сроком действия 8 часов. Клиент получает идентификатор и передает его в заголовке `Authorization: Bearer <идентификатор>`.
- Неверный пароль и несуществующий логин дают одинаковый ответ 401 с одинаковым текстом (SR-06).
- Все точки входа, кроме `GET /health` и `POST /auth/login`, проходят одну общую проверку до вызова обработчика. Проверка ищет сессию по идентификатору из заголовка. Если заголовка нет, сессия не найдена или срок истек, сервер отвечает 401 и обработчик не вызывается. Точка входа считается требующей входа, если для нее явно не указано обратное.
- По найденной сессии сервер загружает учетную запись и ее роль из хранилища при каждом запросе. Обработчики получают субъекта только из этого серверного контекста. Модели запросов не содержат полей автора и роли, а лишние поля в теле запроса не используются.

Решение принимает веб-API. Доверенные данные: хранилище сессий и учетных записей. Из запроса сервер берет только идентификатор сессии, и тот проверяется по хранилищу.

**Поведение при сбое:** если хранилище недоступно или поиск сессии завершился ошибкой, запрос отклоняется без вызова обработчика, данные не возвращаются. Вход при ошибке хранилища идентификатор не выдает.

**Обоснование:** идентификатор сессии нельзя угадать или изготовить: он случайный и действует, только если запись о нем есть в хранилище. Роль читается из хранилища, а не из запроса, поэтому указание роли в запросе ничего не меняет (SR-03), а автор записи всегда равен вошедшей учетной записи (SR-05). Общая проверка до обработчиков не дает забыть вход в новой точке входа (SR-06).

**Принципы проектирования:** полное посредничество (одна проверка перед всеми обработчиками), безопасное значение по умолчанию (точка входа без явной отметки требует вход).

**Рассмотренная альтернатива:** самодостаточный подписанный токен, в котором записаны учетная запись и роль, без обращения к хранилищу. Отклонена: изменение роли и отзыв доступа не действуют до истечения срока токена (ASVS v5.0.0-8.3.2), а ключ подписи нужно хранить вне репозитория. Условие пересмотра: несколько экземпляров сервиса или нагрузка, при которой чтение сессии из хранилища на каждый запрос становится заметным.

**Связанные угрозы:** T-06, T-03, T-05

**Связанные требования:** SR-06, SR-03, SR-05

**Предположения:**

- генератор идентификаторов криптографически стойкий;
- все точки входа регистрируются в веб-API через общий механизм, обходного маршрута к обработчикам нет;
- идентификатор сессии не записывается в журнал сервера;
- трафик не выходит за пределы стенда (А1).

**Будущая проверка:** опирается на критерии приёмки SR-06 (пункты 1 и 2), SR-03 (пункт 2) и SR-05 (пункт 2) и проверяет механизм сессии.

- **Условие:** учетная запись пользователя A и специалиста S1; A выполнил вход и получил идентификатор; есть сессия с истекшим сроком; составлен список всех точек входа API.
- **Действие:** для каждой точки входа, кроме `GET /health` и `POST /auth/login`, отправить запрос без заголовка, со случайным идентификатором той же длины, с идентификатором A, в котором изменен один символ, и с истекшим идентификатором. Выполнить вход с неверным паролем A и с несуществующим логином. От имени A отправить сообщение и запрос на взятие в работу с полями `authorId` S1 и `role` специалиста. Изменить роль A в хранилище и повторить запрос с тем же идентификатором. Просмотреть код создания идентификатора и журнал сервера.
- **Ожидаемый результат:** все запросы с недействительным идентификатором получают 401, данные в хранилище не меняются. Ответы на неверный пароль и несуществующий логин совпадают. Сообщение A сохранено с автором A, взятие в работу отклонено. После изменения роли следующий запрос выполняется с новой ролью без повторного входа. Идентификатор создается криптографически стойким генератором и не встречается в журнале.

**Ограничения и последствия:**

- решение не ограничивает число попыток входа и не защищает от подбора пароля (T-07);
- трафик не шифруется: при доступе по сети идентификатор можно перехватить (А1, отклоненный кандидат модели угроз);
- похищенный идентификатор действует до истечения срока (T-10); явного выхода в минимальном ядре нет;
- идентификаторы сессий хранятся в базе в открытом виде; копия файла базы дает действующие сессии на срок до 8 часов (T-10, А3);
- время ответа на неверный пароль и несуществующий логин может различаться, одинаковыми гарантируются только код и текст ответа;
- каждый запрос читает сессию и учетную запись из хранилища.

### D-02. Единая проверка доступа к обращению по данным из хранилища

**Контекст:** номер обращения приходит от клиента (TB-1), подставить чужой номер просто (T-01). Пользователь может напрямую вызвать операции специалиста (T-03), специалист может обратиться к обращению другого ответственного (T-04). Скрытая кнопка в клиенте эти запросы не останавливает. Без решения пользователь читает чужую переписку, а обращения закрываются без участия ответственного.

**Место в архитектуре:** процесс «Операции с обращениями»; граница TB-2.

**Решение:**

- Каждая операция с обращениями вызывает одну функцию доступа веб-API до любых изменений. Функция получает субъекта из D-01, операцию и, для операций с конкретным обращением, обращение, загруженное из хранилища по номеру. Функция разрешает только перечисленное:

  | Операция | Пользователь | Специалист |
  | --- | --- | --- |
  | создание обращения | да, автором записывается субъект | нет |
  | список обращений | только свои | все |
  | просмотр обращения | автор обращения | любое обращение |
  | сообщение | автор, обращение не закрыто | ответственный, обращение в работе |
  | повторное открытие | автор, обращение закрыто | нет |
  | заметка | нет | ответственный, обращение в работе |
  | закрытие с решением | нет | ответственный, обращение в работе |
  | взятие в работу | нет | обращение новое, ответственного нет |

  Все, чего нет в таблице, запрещено. Условия состояния (не закрыто, в работе, новое) взяты из правил продукта и проверяются в той же функции.
- Для пользователя функция сначала проверяет, что он автор обращения, и только потом проверяет состояние. Поэтому сообщения о состоянии вроде «обращение закрыто» пользователь получает только по своим обращениям.
- Пользователь получает на чужое обращение тот же ответ 404, что и на несуществующий номер. Специалист при запрещенной операции получает 403.
- Список `GET /tickets` для пользователя строится запросом к хранилищу с условием «автор равен субъекту из D-01». Параметры запроса в это условие не попадают.
- Изменение записывается в хранилище только после разрешения; при отказе запись не выполняется.

Решение принимает веб-API. Доверенные данные: субъект и роль из D-01, автор, ответственный и состояние обращения из хранилища. Из запроса берется только номер обращения, и он лишь выбирает запись.

**Поведение при сбое:** если обращение не удалось загрузить или функция доступа завершилась ошибкой, операция не выполняется и ничего не записывается. Ответ об ошибке строится по правилам D-03.

**Обоснование:** право проверяется на сервере для каждой операции по фактическим данным обращения, поэтому подстановка номера или прямой вызов операции не дают доступа (SR-01, SR-03, SR-04). Одинаковый ответ на чужое и несуществующее обращение и порядок проверок не подтверждают пользователю, что обращение с таким номером существует. Правила в одной таблице легче проверить целиком, чем проверки, разбросанные по обработчикам.

**Принципы проектирования:** полное посредничество (одна функция для всех операций), безопасное значение по умолчанию (не указанное в таблице запрещено), минимальные привилегии (пользователь получает доступ только к своим обращениям, специалист изменяет только назначенные).

**Рассмотренная альтернатива:** отдельная проверка прав внутри каждого обработчика. Отклонена: при добавлении новой операции проверку легко пропустить, а правила одной таблицы разойдутся по разным местам кода. Условие пересмотра: правила доступа начнут сильно различаться по операциям, и одна таблица перестанет их понятно описывать.

**Связанные угрозы:** T-01, T-03, T-04

**Связанные требования:** SR-01, SR-03, SR-04

**Предположения:**

- субъект и роль определены по D-01;
- все операции с обращениями вызывают функцию доступа, других путей к записи обращения в веб-API нет;
- автор, ответственный и состояние читаются из хранилища в том же запросе, где принимается решение.

**Будущая проверка:** опирается на критерии приёмки SR-01 (все пункты), SR-03 (пункты 1 и 3) и SR-04 (все пункты) и проверяет единую функцию доступа.

- **Условие:** пользователи A и B, специалисты S1 и S2; обращение X автора A назначено S1 и находится в работе; обращение Y автора A новое; обращение Z автора A закрыто; номер N не существует.
- **Действие:** от имени B вызвать для X и для Z все точки входа `/tickets/{id}`, запросить номер N, запросить список обращений с параметром автора A. От имени A вызвать взятие в работу, заметку и закрытие для Y. От имени S2 вызвать для X сообщение, заметку, закрытие и взятие в работу. Сохранить записи X и Z в хранилище до и после серии запросов. Затем выполнить допустимые действия: A пишет сообщение в X и открывает Z повторно, S1 закрывает X с решением.
- **Ожидаемый результат:** ответы B для X, Z и N совпадают по коду и тексту и не содержат данных обращений, в том числе сведений о состоянии Z. Список B не содержит обращений A. Запросы A к операциям специалиста и запросы S2 к X отклонены. Записи X и Z до и после серии запрещенных запросов одинаковы. Допустимые действия A и S1 выполнены.

**Ограничения и последствия:**

- специалисты читают все обращения по правилам продукта, решение это чтение не ограничивает;
- ответ 404 не скрывает, сколько обращений существует, если номера выдаются по порядку;
- при появлении переназначения или новой роли таблицу правил нужно пересмотреть.

### D-03. Состав ответа определяется ролью получателя

**Контекст:** заметки относятся к тому же обращению, которое пользователь законно открывает (T-02). Проверка доступа D-02 разрешает автору просмотр, поэтому заметки защищает не она, а состав ответа. Если ответ строится из полной записи обращения, заметки попадут к пользователю без всякой атаки, в обычном сценарии.

**Место в архитектуре:** поток «обращение без заметок» от веб-API к пользователю; хранилище SQLite.

**Решение:**

- Заметки и сообщения хранятся в разных таблицах хранилища. Запросы для пользователя к таблице заметок не обращаются.
- Веб-API не отдает записи хранилища напрямую. Для обращения есть две модели ответа. Модель для пользователя содержит тему, описание, состояние, сообщения и решение и не имеет поля заметок. Модель для специалиста дополнительно содержит заметки с автором и временем. У каждого сообщения указаны автор и его роль, чтобы сообщение пользователя нельзя было принять за ответ специалиста (SR-05). Модель выбирает сервер по роли из D-01.
- Список обращений для всех ролей отдается в краткой модели без сообщений и заметок.
- Ответы операций записи (создание сообщения, повторное открытие) строятся по тем же моделям и заметок не содержат.

Решение принимает веб-API при формировании ответа. Доверенные данные: роль из D-01.

**Поведение при сбое:** необработанная ошибка возвращает клиенту общий ответ 500 без подробностей и данных обращения; подробности пишутся только в журнал. Страница ошибки для разработчика, которую ASP.NET Core по умолчанию показывает в окружении `Development`, на стенде отключается, потому что стенд запускается именно в этом окружении.

**Обоснование:** у модели пользователя нет поля для заметок, поэтому заметку нельзя вернуть пользователю из-за ошибки заполнения или забытой очистки поля. Раздельное хранение не дает заметкам попасть в выборку сообщений. Пользователь не видит и пустого поля заметок, то есть не узнает, есть ли заметки вообще (SR-02).

**Принципы проектирования:** минимизация поверхности воздействия (в ответе пользователю нет поля, через которое заметки могли бы утечь), минимальные привилегии на уровне данных (пользователь получает только нужные ему поля).

**Рассмотренная альтернатива:** одна модель обращения с полем заметок, которое сервер очищает перед отправкой пользователю. Отклонена: защита держится на том, что очистку не забудут ни в одной точке входа, а пустое поле все равно показывает пользователю наличие такого раздела. Условие пересмотра: появятся поля, видимость которых зависит не только от роли, но и от других условий; тогда понадобится общий механизм фильтрации полей.

**Связанные угрозы:** T-02

**Связанные требования:** SR-02

**Предположения:**

- роль получателя определена по D-01;
- каждая новая точка входа, которая возвращает обращение пользователю, использует модель пользователя;
- заметки передаются специалисту в составе ответа на запрос обращения (А6).

**Будущая проверка:** опирается на критерий приёмки SR-02 (все пункты) и проверяет выбор модели ответа.

- **Условие:** в обращении пользователя A есть два сообщения и заметка специалиста S1 с уникальной строкой-меткой в тексте.
- **Действие:** от имени A запросить обращение и список обращений, отправить сообщение, вызвать операцию над заметками и вызвать ошибку запросом с некорректным телом; в каждом ответе искать строку-метку и имя поля заметок. Затем запросить обращение от имени S1.
- **Ожидаемый результат:** ни в одном ответе для A нет строки-метки и поля заметок, включая ответы операций записи и ответы об ошибке. Ответы об ошибке не содержат подробностей исключения. В ответе для S1 заметка есть с автором и временем.

**Ограничения и последствия:**

- решение не защищает от того, что специалист сам напишет служебные сведения в сообщение пользователю;
- все специалисты читают заметки любого обращения;
- для двух ролей поддерживаются две модели ответа, и при изменении обращения их нужно обновлять вместе.

### D-04. Начальные учетные записи вне репозитория и пароли в виде медленного хеша

**Контекст:** учетные записи создаются из конфигурации стенда (А4), а файлы настроек `appsettings*.json` лежат в публичном репозитории (T-08). Если записать туда пароли или хранить их в базе в открытом виде, любой, кто видит репозиторий, файл базы или журнал, входит от чужого имени, в том числе как специалист.

**Место в архитектуре:** конфигурация стенда, хранилище учетных записей, журнал сервера; граница TB-3.

**Решение:**

- Логины, роли и пароли начальных учетных записей задаются через секреты пользователя .NET (user secrets) или переменные окружения стенда. ASP.NET Core читает оба источника наряду с `appsettings*.json`, но секреты пользователя хранятся в профиле пользователя вне папки проекта, а переменные окружения не попадают в файлы. В репозитории остается только описание нужных ключей без значений.
- При создании учетной записи сервер сохраняет не пароль, а результат PBKDF2-HMAC-SHA256 с 600 000 итераций и случайной солью 16 байт для каждой учетной записи. Соль и число итераций хранятся рядом с результатом. При входе введенный пароль обрабатывается так же, и результаты сравниваются за постоянное время.
- Журнал сервера не записывает тела запросов; код входа не пишет пароль в журнал.

Решение принимает веб-API при создании учетных записей и при входе. Доверенный источник паролей: конфигурация стенда, которую задает владелец (А3).

**Поведение при сбое:** если начальная учетная запись задана без пароля или с пустым паролем, сервер ее не создает и пишет в журнал имя ключа без значения.

**Обоснование:** в репозитории и в файле базы нет значения, из которого пароль получается без подбора (SR-07). Медленная функция с солью делает подбор по копии базы дорогим, а одинаковые пароли дают разные сохраненные значения. PBKDF2 входит в стандартную библиотеку .NET и не требует сторонних пакетов; число итераций взято из рекомендации OWASP Password Storage Cheat Sheet для PBKDF2-HMAC-SHA256.

**Принципы проектирования:** минимизация поверхности воздействия (в репозитории и журнале нет секретов).

**Рассмотренная альтернатива:** Argon2id, который OWASP ставит на первое место. Отклонен для учебного стенда: в стандартной библиотеке .NET его нет, нужен сторонний пакет. Условие пересмотра: размещение сервиса вне учебного стенда.

**Связанные угрозы:** T-08

**Связанные требования:** SR-07

**Предположения:**

- владелец стенда и его компьютер доверенные (А3), поэтому секреты пользователя в профиле не шифруются и это допустимо;
- пароли учебных учетных записей нигде больше не используются.

**Будущая проверка:** опирается на критерий приёмки SR-07 (все пункты) и проверяет хранение и источник паролей.

- **Условие:** две учетные записи созданы из секретов пользователя с одинаковым паролем; выполнены один успешный и один неуспешный вход.
- **Действие:** найти пароль в файле базы, в журнале сервера, в файлах репозитория и во всех коммитах истории; сравнить сохраненные значения двух учетных записей.
- **Ожидаемый результат:** пароль нигде не найден; сохраненные значения двух учетных записей различаются; в базе для каждой учетной записи есть соль, число итераций и результат функции.

**Ограничения и последствия:**

- секреты пользователя предназначены только для разработки и не шифруются; для размещения вне стенда нужен другой способ хранения секретов;
- решение не защищает от подбора пароля через API (T-07);
- PBKDF2 хуже Argon2id противостоит подбору на специализированном оборудовании;
- перед первым запуском владелец стенда должен задать секреты, и раздел 10 паспорта нужно будет дополнить этим шагом при реализации.
